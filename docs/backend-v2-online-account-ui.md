# Backend V2 online-account UI

Companion to [`docs/backend-v2-client.md`](backend-v2-client.md) (the typed client layer, issue #158)
and [`docs/backend-v2-correspondence-ui.md`](backend-v2-correspondence-ui.md) (the Multiplayer screen's
own, fallback-only sign-in panel). This document covers the first-class, player-facing
register/sign-in/sign-out/self-profile screen reachable from the Account hub.

## Local profile identity vs Backend V2 online identity

These are, and remain, two completely independent identities:

| | Local profile | Backend V2 online account |
| --- | --- | --- |
| Owner | `LocalAccountIdentity.UserId`/`UserName` (`GameOptions.userid`/`userName` forward here) | `BackendV2SessionStore.Current.PlayerId` |
| What it is | Which local save/progression profile is selected on this device - "a local selection only, it proves nothing about authentication" (see `LocalAccountIdentity`'s own doc comment) | Who is signed in to Backend V2 - match results, leaderboards, friends, correspondence |
| Created/changed by | `AccountManager` (`level_00_account_createNew`/`_loginExisting`/`_loginLocal`), legacy `APIHelper`/`UserModel` | `OnlineAccountController` (`level_00_account_online`), `BackendV2Runtime.Session` |

**The online-account screen never reads or writes local profile identity**, and registering, signing
in, or signing out of a Backend V2 account never changes which local profile is selected, never creates
or touches a local SQLite `User` row, and never implies any sync between local progression and the V2
player. `Level5BackendV2ArchitectureTests.OnlineAccountControllerNeverUsesLocalProfileIdentity`
enforces this at the source-text level (no `GameOptions.userid`/`userName`/`APIHelper`/`UserModel`
reference anywhere in `OnlineAccountController.cs`).

## Where it lives

| Piece | Path | Assembly |
| --- | --- | --- |
| Screen (MonoBehaviour) | `Assets/Scripts/menu_login/OnlineAccountController.cs`, `OnlineAccountUiObjects.cs` | default (`Assembly-CSharp`) |
| Orchestration / view state | `Assets/Scripts/backendv2/Level5BackendV2/UI/OnlineAccountCoordinator.cs` | `Level5.BackendV2.asmdef` |
| Scene | `Assets/Scenes/level_00_account_online.unity` (generated by `Assets/Level5/Editor/OnlineAccountSceneBootstrap.cs`, menu `Tools/Backend V2/Generate Online Account Scene`) | - |
| Entry point | a button on the Account hub (`level_00_account`, `AccountHubUiObjects.onlineAccountButton`) | default |

`OnlineAccountController` lives in the default assembly for the same structural reason
`CorrespondenceScreenController` does: it needs `MenuFooterUiObjects`/`Constants`/scene navigation,
which have no assembly definition of their own. `OnlineAccountCoordinator` holds no UI reference at
all - same split as `FriendsCoordinator`/`ChallengeCoordinator` - so it is fully unit-testable against
`FakeApiTransport` with no scene involved
(`Assets/Tests/Editor/Level5BackendV2OnlineAccountCoordinatorTests.cs`).

## UI flow

- **Signed-out**: a sign-in group (username, password, Sign In) and a register group (username,
  password, display name, Register), each with its own error text. Empty-field checks only - the
  backend remains authoritative for username grammar, password policy, uniqueness, and display-name
  limits. No pre-login/pre-register username-existence check is ever made.
- **Signed-in**: display name, player tag, Sign Out, and a status/error text with a Retry button for a
  transient self-profile read failure. Login/Register controls are not shown while signed in -
  switching accounts always requires an explicit Sign Out first;
  `OnlineAccountCoordinator.SignIn`/`Register` refuse to start at all while a session already exists.
- **Opening the screen**: if a session already exists (restored at app startup, or from an earlier
  visit), the screen skips straight to fetching and showing the self-profile - it never requires a
  fresh login just because the screen reopened.
- **A transient self-profile read failure** (network/timeout/server/rate-limit) leaves the session and
  signed-in identity untouched; only `Profile` stays unset and a retryable error is shown. This path
  never calls `BackendV2SessionStore.Clear()` or `Session.Logout`.
- **Sign Out** always ends signed-out locally, even if the server call fails or the device is offline -
  the same contract `BackendV2SessionManager.Logout` already guarantees.

## Self-profile client contract

`IPlayersApiClient.GetMyProfile()` (`GET api/v2/players/me/profile` -> `PlayerProfileResponseDto`:
`PlayerId`/`DisplayName`/`Tag`) is additive - it does not change `GetMe()`'s existing frozen bare-`Guid`
contract (`GET api/v2/players/me`), which other production code already depends on. See
`docs/backend-v2-client.md`.

## Known limitations

- No email registration, email verification, password reset, or MFA - matches the current Backend V2
  account contract (username/password/displayName only).
- No display-name/tag editing from this screen (`IPlayersApiClient.UpdateMe` exists but is out of
  scope here).
- No legacy-account migration or V1/V2 account linking - registering or signing in to a Backend V2
  account never touches the legacy `UserModel`/local `User` table.
