## Shared end, result, persistence and Backend policies

Ordinary countdown endings use the primary human's grounded state and primary ball's not-thrown predicate; injected timer expiry in the probes deliberately sets those predicates. This exercises the real `Timer.Update` → end request → result path without waiting the full authored 70/120 seconds. It does not establish CPU final-shot grace or fairness policy. Marker completion requests the existing ending; `MatchLifecycle` accepts the first cause, so later requests cannot replace it. F3 uses initialized nonempty successful marker state at that accepted ending rather than treating every `Unknown` cause as success.

Primary death reaches `GameRules` through the actual health event plus existing poll fallback. Duplicate end requests do not produce duplicate completed work. Accepted elapsed time is frozen before presentation and retry work. Ordinary timed/Spot-Up/combat quit or restart aborts without synthesizing a completed result. Free Play has explicit save adapters on quit/menu/restart; Arcade's lack of that explicit policy is preserved, not silently repaired. Campaign retains its end-round owner, two initial normal continues/zero Hardcore, tie retry without consumption, loss retry with consumption, and finality by route-list position.


The last destination is the approved Dev scene, even though its stable ID and scene-number naming differ from ordinary level visibility. All 21 destinations are enabled. `EndRoundMenuManager` owns advancement and aggregate terminal persistence; hidden route entries must not be resolved by pretending they are ordinary menu selections.

`HighScoreModel` snapshots stable mode/arena/character IDs, modifiers, primary points, per-range and aggregate makes/attempts, distance, streak, kills and elapsed time. Ordinary results first become durable in SQLite or `PendingMatchPersistenceStore`; only then does the existing Backend submission adapter try to enqueue. Failed Spot-Up skips the ordinary completion-time result/submission, not all-time or XP processing. Campaign aggregate and explicit Free Play saves remain their own paths. Competitive attempts/competition-only simultaneous result handling remain separate and are not certified by this audit.

All-time statistics use their existing session/result ledger. Character progression uses SQLite, existing progression result IDs/ledger and account-scoped `PendingProgressionStore` JSON repair. Existing combat/campaign tests provide separate seeded progression/durability checks.
