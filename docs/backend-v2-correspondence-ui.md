# Backend V2 correspondence UI (issue #159)

Companion to [`docs/backend-v2-client.md`](backend-v2-client.md) (the typed client layer, issue
#158) and [`docs/versus-architecture.md`](versus-architecture.md) §10. This document covers the
player-facing screen built on top of that client layer, and points at
[`docs/backend-v2-correspondence-certification.md`](backend-v2-correspondence-certification.md)
for end-to-end certification evidence.

## Where it lives

| Piece | Path | Assembly |
| --- | --- | --- |
| Screen (MonoBehaviour) | `Assets/Scripts/menu_multiplayer/CorrespondenceScreenController.cs` | default (`Assembly-CSharp`) |
| Launch orchestration | `Assets/Scripts/versus/RemoteAttemptLauncher.cs`, `RemoteAttemptLaunch.cs` | default (`Assembly-CSharp`) |
| Coordinators / view state | `Assets/Scripts/backendv2/Level5BackendV2/UI/` | `Level5.BackendV2.asmdef` |
| Session persistence | `Assets/Scripts/backendv2/Level5BackendV2/Session/BackendV2SessionPersistenceStore.cs`, `BackendV2SessionPersistenceBootstrap.cs` | `Level5.BackendV2.asmdef` |
| Result-submission retry | `Assets/Scripts/backendv2/Level5BackendV2/Correspondence/PendingRemoteAttemptResult.cs` + additions to `RemoteAttemptResultSubmitter.cs` | `Level5.BackendV2.asmdef` |
| Scene | `Assets/Scenes/level_00_multiplayer.unity` (generated by `Assets/Level5/Editor/BackendV2CorrespondenceSceneBootstrap.cs`, menu `Tools/Backend V2/Generate Correspondence Scene`) | - |
| Entry point | `Multiplayer` button on `level_00_start`'s footer (`StartManager.LoadMultiplayerMenu`) | default |

The footer prefab has not been given its own authored Multiplayer button (that needs Editor/
prefab-authoring access this change did not have): `StartManager.EnsureMultiplayerButton` clones one
from the account button at runtime instead, the first time it is needed. `SpliceIntoExplicitNavigation`
patches the clone into the account button's Explicit-mode keyboard/gamepad navigation chain
(splices in as account's new right-neighbor, repoints whatever used to be account's right-neighbor
back at the clone) so it is reachable, not just clickable - a no-op if the footer's navigation mode
is Automatic instead. A later pass should author the button into the prefab properly, at which point
`EnsureMultiplayerButton` and the splice both become no-ops (the footer already has its own button).

**Why the launcher and the screen live in the default assembly, not `Level5.BackendV2.asmdef`:**
both need `LegacyGameOptionsBridge` (the one-way push from a validated `MatchConfiguration` into the
legacy `GameOptions` globals every unmigrated gameplay script still reads) and, for the screen,
`Constants`/scene navigation. `LegacyGameOptionsBridge` has no assembly definition of its own, and a
custom assembly definition can never reference Unity's implicit default assembly - this is a hard
engine restriction, not a choice either #158 or #159 made. `VersusLauncher` (the local-play
equivalent) lives in the same place for the same reason. `BackendV2CoroutineHost` and
`BackendV2ErrorMessages` are `public` (not `internal`) specifically so this default-assembly code
can reach them.

## UI flow

One scene, seven sub-panels rendered into a single content area (not seven persistent panel
GameObjects - the coordinators below already hold each tab's state, so switching tabs just
re-renders from that state rather than needing seven parallel hierarchies):

- **Friends** - resolve-by-tag + send request, incoming/outgoing friend requests
  (accept/decline/cancel), friends list (remove, or start a challenge from that row).
- **Incoming Challenges** - `ICorrespondenceApiClient.ListIncoming`, accept/decline.
- **Outgoing / Waiting** - `ListOutgoing`, cancel.
- **Your Turn** - `ListActive`, filtered to rows this player has not yet completed their current
  attempt for (see "Whose turn" below), with a Play action.
- **Active Series** - every `ListActive` row, badged with whose turn it is.
- **Completed** - `ListCompleted`, read-only. Scoped to series that actually finished play only.
- **History** - `ListHistory`, read-only. Every terminal series either participant is in -
  Completed, Declined, Cancelled, or Expired - each row labelled with its status. The durable
  correspondence-history view: unlike the other tabs, these rows never disappear on their own.

Reconnect/resume (screen open, or `Start()` after a scene load): checks
`BackendV2SessionStore.IsAuthenticated` and shows an inline sign-in form if not (no separate login
scene), then refreshes every list from Backend V2 before rendering anything, then surfaces a
pending-result banner if one exists. Nothing is rendered from a previous session's leftover state.

## Backend V2 client usage / state ownership

Every network call goes through `BackendV2Runtime.Players` / `.Friends` / `.Correspondence` /
`.Session` - never a raw `UnityWebRequest`, never the legacy `APIHelper`
(`Level5BackendV2ArchitectureTests.NothingInTheClientOrUiLayerIssuesARawUnityWebRequest` /
`NothingInTheClientOrUiLayerCallsLegacyApiHelper` enforce this for the whole `backendv2/` tree,
which includes the `UI/` coordinators).

The UI/app layer holds only view state - which tab is selected, loading/error flags, the last
fetched DTO snapshot, an opaque pagination cursor (forwarded verbatim, never parsed), which row has
a command in flight:

- `ListViewState<T>` - items/loading/error/cursor, shared by every list (friends, both friend-request
  lists, all four series lists).
- `RowCommandState` - which row (by id) has a command outstanding; a coordinator refuses a second
  concurrent command for the same row rather than merely disabling a button a player could still
  tap (see `Level5BackendV2FriendsCoordinatorTests`/`Level5BackendV2ChallengeCoordinatorTests`).
- `ChallengeFormState` - the create-challenge draft, including the retry-stable `clientRequestId`
  (below).
- `ActiveSeriesTurnClassifier` - caches, per series id, whose turn it is (from a detail fetch), so
  the Active and Your Turn tabs share one classification pass instead of each re-fetching.

Backend V2 remains the sole authority for everything else: challenge/series status, frozen rules,
attempt identity, accepted results, game/series resolution, sealed-result disclosure. The UI never
infers or caches a decision Backend V2 owns - every mutating command re-fetches the lists it
affects afterward rather than guessing the new state locally.

### Whose turn (`SeriesRowClassifier`)

A `SeriesSummaryDto` (what the list endpoints return) does not say whose turn it is - only a detail
fetch (`SeriesResponseDto`, with its `Games[]`) does. `SeriesRowClassifier.ClassifyTurn` reads only
`Games[CurrentGameNumber].YourAttempt` (presence, and its `Status`) - **never**
`OpponentAttempt`, which is exactly the field the server's own sealed-result projection may still be
withholding. Ambiguous cases default to "your turn": starting an attempt that is not actually
available is safely refused server-side, whereas wrongly defaulting to "opponent's turn" would hide
an actionable turn from the player. The exact string Backend V2 uses for a completed attempt's
`Status` is inferred as `"Completed"` (consistent with the `"Pending"`/`"Active"` series-status
values already confirmed in `Assets/Tests/Editor/BackendV2Fixtures.cs`) - confirm this against the
live backend as part of certification (see the certification doc's notes).

**Cost note:** classifying the Active tab is one detail fetch per row (`ICorrespondenceApiClient.Get`)
- O(n) per page. Acceptable at correspondence scale (a handful of concurrent series per player);
not optimized further, since adding a server-side "whose turn" filter is a backend change and out
of scope for this issue.

## Retry behavior

**Challenge create** (`ChallengeFormState.GetOrBeginClientRequestId`): a `clientRequestId` is
generated once per logical "create this challenge" action and reused across a retry of that exact
action - `ChallengeCoordinator.Create` never generates a new one on its own. The screen decides
when a submission is *definitive* (success, or a `Validation` failure - the player must change the
form) versus merely *retryable* (network/server failure - tapping "Send Challenge" again should
resend the identical request): only a definitive outcome calls
`ChallengeFormState.CompleteSubmission()`, which clears the id so a later, genuinely new challenge
gets a fresh one.

**Result submission** (`RemoteAttemptResultSubmitter` + `PendingRemoteAttemptResult`): unchanged
from #158 up to the point a submission fails for a retryable reason (network/server/validation/auth
- everything except success or `Conflict`, which already meant "the domain decided this, do not
retry"). What #159 adds: the exact metrics dictionary built for that submission is stashed in
`PendingRemoteAttemptResult` *before* the network call, not discarded when the coroutine returns -
by the time a player is looking at a "resend result" prompt, the `GameStats` it came from may no
longer exist, so this is the only way to satisfy "retry the same payload, never rebuild a different
one." `RemoteAttemptResultSubmitter.TryRetryPending()` is the UI's one entry point for this, reusing
the same `TryClaim`/`Release` guard `TrySubmit` already used, so a UI-triggered retry cannot race a
still-in-flight automatic one.

## Pending result submission banner

`PendingRemoteAttemptResult.HasPending` is checked every time the screen opens/resumes and every
time a tab re-renders. If true, a banner with a "Resend result" button is shown above the current
tab's content; tapping it calls `TryRetryPending()`. This is the only UI surface for a stuck
submission - there is no separate "pending" scene or modal.

## Launching a turn

`RemoteAttemptLauncher.Run` (driven directly as an `IEnumerator` by the screen's own coroutine, not
via the fire-and-forget `Launch` entry point `RemoteAttemptResultSubmitter` uses from the match-end
hook - the screen is a natural owning `MonoBehaviour` and outlives nothing this needs):

0. Refuses to start (before any network call) if `PendingRemoteAttemptResult.HasPending` - both it
   and `ActiveRemoteAttempt` are single global slots (the same shape as `ActiveMatch`/
   `ActiveVersusAttempt`: "the one match/attempt currently being played"), so beginning a new attempt
   while an earlier one's failed result is still awaiting retry would silently overwrite and lose it.
   The player must resend (successfully, or to a definitive failure) that pending result first.
1. `ICorrespondenceApiClient.StartAttempt` - failure surfaces as an inline error, mutates nothing.
2. `RemoteAttemptDescriptorMapper.Map` (unchanged from #158) - failure (unsupported protocol
   version, unknown ruleset, unplayable ruleset version, unknown required metric) surfaces the same
   way; `ActiveMatch.Begin`/`ActiveRemoteAttempt.Begin` are never called on a mapping failure.
3. On success: `ActiveMatch.Begin`, `ActiveRemoteAttempt.Begin`, `LegacyGameOptionsBridge.Apply`,
   `SceneTransition.LoadScene` - the same sequence `VersusLauncher.Launch` uses for local play.

**Known limitation:** no level picker exists yet for a remote attempt - it launches with a fixed
default level. This mirrors local versus play, which also has no production launch UI yet
(`VersusLauncher.Launch`'s only caller before this issue was `VersusDevConsole`, a dev-only tool). A
level picker for versus play in general is future work, not something #159 introduces a gap in.

Character selection is no longer a limitation (#179): `RemoteCharacterSelectionResolver` resolves the
current local primary character - the same stable id `PlayerSelectionSession`/`PlayerSelectionController`
use for ordinary local launches - into a `CharacterSelection` before `RemoteAttemptLauncher.Run` is
called, so a resolution/lock failure is shown inline and never reaches `StartAttempt`. No
correspondence-specific character picker or character state was introduced.

## Refresh-token persistence

`BackendV2SessionStore.Changed` fires on every `Set`/`Clear` (including a silent background token
refresh inside `AuthenticatedApiClientBase` that never goes through an explicit login/logout call).
`BackendV2SessionPersistenceBootstrap` subscribes to it and mirrors the session to
`Application.persistentDataPath/backendv2_session.json` via `AtomicFile` - plaintext JSON, the same
storage convention every other local save in this project already uses
(`CharacterProgressStore`, `FileVersusSeriesRepository`, `PendingProgressionStore`), with no
additional OS-keychain/secure-storage layer. A refresh token is a bearer credential: this is a
deliberate, accepted tradeoff (matching the project's existing local-save security posture), not an
oversight - `BackendV2SessionStore.cs` previously left this decision open explicitly.

`BackendV2SessionPersistenceBootstrap.EnsureInitialized()` is idempotent and is called from two
places: `UserAccountManager.Awake()` - the real production ownership, since the build's first scene
is `level_00_account_loginLocal`, making a persisted Backend V2 session available application-wide
(MatchResult submission, leaderboard reads, ...) rather than only after a player opens Multiplayer -
and `CorrespondenceScreenController.Awake()`, kept as a no-op fallback for any path that opens the
correspondence screen directly (a test, a dev shortcut) without going through the local-account
scene first. Not a `[RuntimeInitializeOnLoadMethod]`. That was the first approach and it broke the
EditMode test suite: Unity 6000.5.7f1's batchmode EditMode test runner still fires
`[RuntimeInitializeOnLoadMethod]` methods, so the very first `BackendV2SessionStore.Set` call
anywhere in the ~1600-test suite started writing a real session file to disk as a side effect of
unrelated tests (see the doc comment on `BackendV2SessionPersistenceBootstrap` for the full
account). An EditMode test never loads either scene, so this never fires during one.

On the first of those calls, a saved session is loaded from disk and set in memory - nothing more.
The bootstrap performs zero network requests, so a temporary Backend V2 outage at app launch cannot
delete an otherwise locally valid persisted session. A restored session means the credentials are
locally available for this process, not that the server has confirmed them this session; that
confirmation is the existing authenticated-request pipeline's job. The first authorized request
after restoration runs the normal `AuthenticatedApiClientBase` -> `BackendV2SessionManager.
EnsureFreshAccessToken` path (refreshing first only if the access token looks close to expiring by
the client's own clock), and a `401` still triggers the normal `ForceRefresh` + retry-once path. A
refresh failure at that point clears both the in-memory and persisted session, and the screen's
normal "not authenticated" path prompts for login - the same definitive-invalidation behavior as
before, just triggered by an actual request instead of by restoration itself.

## Known limitations / deferred work

- No automatic retry/backoff for list refresh - lists refresh on tab open and after an explicit
  action, never on a timer.
- Unlock-state revalidation for a network-driven match launch remains open (the existing
  `VersusLauncher` gap noted in `docs/persistence-boundaries.md` applies identically here).
- No level picker (see above); character selection is resolved from existing player-select authority.
- Built entirely at runtime from code rather than authored as a scene/prefab, unlike every other
  menu screen in this project (see the doc comment on `CorrespondenceScreenController` for why -
  in short, this change did not have interactive Editor/prefab-authoring access, and hand-typing
  scene/prefab YAML directly was judged too risky to get right without it). A production pass
  should re-author it as a normal uGUI scene/prefab; the coordinators and launch orchestration
  underneath do not need to change for that.
- Legacy `UnityEngine.UI.Text`/`InputField` rather than TextMeshPro (this project's now-dominant
  text component), for the same reason - a correct runtime `TMP_InputField` hierarchy needs
  Editor-authored sub-objects.
- No gamepad-optimized navigation (`UiSelectionAdapter`/Input System UI module) - a plain
  `StandaloneInputModule` `EventSystem` is used instead, so mouse/keyboard work but the screen does
  not have the same first-class controller navigation other menu screens have.
