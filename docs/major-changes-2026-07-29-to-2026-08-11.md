# Major Changes: 2026-07-29 to 2026-08-11

Last updated: 2026-08-11

This is the human-readable catch-up document for the last two weeks of Level 5 work. It is not a
commit log. It groups the major changes by system, explains why each happened, and points to the
deeper docs that own the details.

## Executive Summary

The project moved from mostly scene/global-driven gameplay state toward explicit, validated runtime
contracts. The biggest changes were:

- Match launch now flows through `MatchRequest`, `PlayerRoster`, `MatchConfigurationBuilder`,
  `MatchConfiguration`, `ActiveMatch` and `MatchRuntime` instead of relying only on process-wide
  `GameOptions` fields.
- Versus/correspondence multiplayer now has a plain-C# domain for rulesets, attempts, games,
  best-of-N series, sealed/open information policy, persistence, versioning and result reporting.
- Player select was refactored toward stable character identity and `PlayerRoster` output rather
  than `StartManager` owning every selection concern.
- Input was modernized through gameplay input readers, reference-counted controls, UI selection
  adapters and reduced direct touch polling.
- Basketball scoring was partially extracted into tested pure functions, and the first made-shot
  result event now exists.
- Character progression and persistence were hardened, including local/offline boundaries,
  atomic-style saves and safer account/stat handling.
- Build, repository and scene validation were tightened to catch dev scenes, missing scripts,
  stale singletons, architecture regressions and repository hygiene before they ship.

## Timeline

### 2026-07-29 to 2026-07-30: Unity Upgrade and Runtime Robustness

The early work stabilized the project after the Unity migration and cleaned up compilation/runtime
breakage. Notable changes included project renaming cleanup, compatibility fixes, non-API script
robustness, API handling fixes and initial player input ownership work.

Result:

- The project compiled again under the newer Unity/editor setup.
- Several fragile runtime null/lifecycle paths were hardened.
- Player input ownership began moving away from direct/global reads.

### 2026-07-31: Persistence, Account and Progression Foundations

This pass added the draft character progression service, then hardened it and adjacent persistence
systems. It also reduced security and privacy risk around score synchronization.

Key changes:

- Character progression draft service and runtime validation.
- Match progression and unlock services.
- Loading, credits, account dialog and campaign-flow lifecycle guards.
- Score IDs moved away from hardware-derived identifiers toward GUIDs.
- Sensitive API payload and identity logging reduced.
- Dynamic SQL identifiers and sort order validated.
- Obsolete Unity API usage reduced in several areas.

Primary docs:

- [Persistence and Account Identity](persistence-boundaries.md)

### 2026-08-02 to 2026-08-05: Architecture Audit Fixes and Combat/Gameplay Hardening

The audit work turned scattered defects into numbered findings and fixed many concrete runtime
issues. This was the stretch where the codebase started getting durable guardrails rather than only
point fixes.

Key changes:

- Systems architecture baseline and architecture audit documents added.
- Combat health contracts introduced.
- Actor damage started routing through shared combat contracts.
- Attack queue reservation and cleanup hardened.
- Player identity, basketball stat ownership, vehicle spawn and match-end bugs fixed.
- Enemy/bodyguard/player combat interactions improved.
- Beat tha Computahs continues reset fixed.
- Player input reader and player input routing added.
- Menu input modernization began for options, credits, account, stats, progression and start menu.

Important fixed risks:

- Shared/static AI state that could cross-contaminate instances.
- Basketball stats being credited to the wrong player.
- Shot attempt flags persisting after misses and double-scoring later makes.
- End-of-match side effects running through fragile per-frame paths.
- Traffic prefab state being mutated before instantiation.

### 2026-08-07 to 2026-08-08: Authored Data and Match Configuration Overhaul

The match system moved toward a typed, validated launch pipeline. This changed the shape of the
game more than any individual feature: modes, levels, rosters, modifiers and resolved rules became
explicit objects rather than scattered globals.

Key changes:

- Authored Level 5 game data exporter and provenance hardening.
- `GameModeId`, `GameModeDefinition`, `LevelDefinition`, `GameModeCatalog`,
  `LevelDefinitionCatalog`, `GameModeCompatibility`, `MatchRequest`,
  `MatchConfigurationBuilder`, `MatchConfiguration`, `ResolvedMatchRules`,
  `PlayerRoster` and related match domain types.
- `ActiveMatch`, `MatchRuntime`, `LevelRuntimeContext` and `MatchController` established as
  scene/runtime bridges.
- Architecture tests added to ratchet down new `GameOptions` and mode-boolean usage.

Result:

- Launch paths can be validated before a scene loads.
- Gameplay can read resolved match rules instead of reconstructing meaning from old static flags.
- The old globals still exist as a compatibility bridge, but they are no longer the desired source
  of truth.

Primary docs:

- [Game Options Match System Overhaul Plan](game-options-match-system-overhaul-plan.md)
- [Generated Game Mode Characterization](generated/level5-game-mode-characterization.md)

### 2026-08-09: Versus/Correspondence Multiplayer Foundation

The project gained a complete first-pass versus domain. Gameplay does not become a multiplayer
system; it produces match metrics, and the versus system compares those metrics across participants
and time.

Key changes:

- `CompetitiveRuleset`, `ComparisonKey`, `AttemptMetric`, `VersusCapability`.
- `Attempt`, `AttemptResult`, `AttemptState`.
- `VersusGame`, `GameResult`, `InformationPolicy`.
- `VersusSeries`, `SeriesFormat`, `SeriesSnapshot`, `SeriesScore`.
- `IVersusSeriesRepository`, in-memory repository, file-backed repository and JSON serializer.
- `VersusRuntime`, `VersusCatalogs`, `DefaultCompetitiveRulesets`, `VersusLauncher`,
  `ActiveVersusAttempt`, `VersusMatchReporter`.
- Edit-mode and play-mode tests covering series lifecycle, information policy, persistence,
  versioning, gameplay reporting and ordinary-match no-op behavior.
- `VersusDevConsole` for exercising local alternating/correspondence flow before production UI
  exists.

Important design decisions:

- Local versus means local alternating attempts, not same-screen simultaneous play.
- A mode must opt in through a ruleset; unsupported modes are refused rather than guessed.
- Async/correspondence support is explicit per ruleset.
- Sealed attempts and open targets are enforced by the domain, not by UI convention.
- Ruleset versions are separate from game build versions.

Primary docs:

### 2026-08-09 to 2026-08-10: Shot Scoring, Assembly Split and Player Select

Basketball and player select both received major boundary work.

Basketball:

- Shot scoring arithmetic moved into `Level5.Core.ShotScoring`.
- Shot modifier arithmetic moved into `Level5.Core.ShotModifiers`.
- Tests pin the existing scoring behavior, including preserved oddities.
- Shot lifecycle documented.
- The first `MadeShotResult` payload and `BasketBallShotMade.ShotResolved` event were added.
- CPU distance scoring now uses the CPU ball's last shot distance instead of `BasketBall.instance`.

Player select:

- Player select overhaul plan created and indexed.
- Selection state moved toward stable character identity and `PlayerRoster` output.
- `StartManager` responsibility started shrinking around player/CPU selection.
- The downstream match configuration pipeline became the target boundary for launching.

Assembly split:

- `Assets/Level5/Core`, constants, audio and pooling are split into asmdefs.
- The remaining `Assets/Scripts` split is blocked by the player/game-manager/basketball cycle and
  several Unity-facing data/persistence seams.
- The immediate direction is to extract events/results and ownership contracts before moving folders.

Primary docs:

- [The Basketball Shot Lifecycle](shot-lifecycle.md)
- [Player Select Architecture Overhaul](player-select-architecture-overhaul-plan.md)

### 2026-08-11: Repository Guards and Save Safety

The latest pass focused on making earlier fixes stick.

Key changes:

- Versus file saves now use the existing atomic file helper instead of deleting the original before
  moving the replacement.
- File-backed versus persistence tests cover save/reload, temp cleanup and archive preservation.
- Dev scene loading is guarded out of release builds.
- `level_23_dev` is disabled in build settings.
- Repository validation now catches enabled dev scenes and missing MonoBehaviour script references.
- Stale missing-script settings assets were removed.
- `PlayerController` no longer falls back to global controls after per-player input resolution
  fails.

Validation:

- `scripts/validate-repository.ps1`
- `dotnet build Level5.sln`
- targeted searches for missing scripts, dev scene exposure and stale shot/input fallbacks

## Current Playable State

Production menu support for versus is not built yet. To exercise the system now, use
`VersusDevConsole`:

1. Add `VersusDevConsole` to a GameObject in a dev/menu scene.
2. Configure participants, `LocalAlternating`, `SealedAttempt`, a ruleset playlist and a level id.
3. Use the component context menu: `Versus/Create series`.
4. Use `Versus/Take next turn` to launch one participant's run.
5. Finish the match normally.
6. Return to the dev console scene and use `Versus/Report` or `Versus/Take next turn`.

The old Versus CPU mode is still ordinary gameplay. It is not the new versus-series feature.

## New Guardrails

The last two weeks added tests and validators that are now part of the architecture:

- Match architecture ratchets: no new `GameOptions` consumers or mode identity booleans.
- Versus architecture ratchets: no scene, filesystem or networking dependencies in the domain.
- Versus information policy tests: no public attempt leaks and no "reveal anyway" view flag.
- Singleton lifetime tests: scene-scoped `instance` fields must clear on destroy.
- Repository validation: dev-code isolation, serialization policy, build-scene policy, selectable
  levels, input actions, gameplay scene objects, enabled dev-scene guard and missing-script guard.
- Shot scoring/modifier tests: scoring behavior and extracted arithmetic are pinned.
- Play-mode coverage: gameplay reporting into versus and singleton teardown.

## What Is Still Not Done

This work intentionally did not finish every refactor it enabled.

- No production versus menu yet.
- No online backend for correspondence yet; file-backed local persistence is the current store.
- `BasketBall` and `BasketBallAuto` still duplicate launch physics, shot meter messaging and UI stat
  formatting.
- `GameStats`, HUD, audio and marker updates still observe/apply made-shot state directly rather
  than fully subscribing to `MadeShotResult`.
- `PlayerController` remains too broad: input, motor, animation, combat and basketball actions are
  still one large surface.
- `GameLevelManager`, `GameRules`, `Pause`, `Timer` and HUD code still carry legacy static/global
  access.
- Full `Assets/Scripts` asmdef separation is still blocked by player/game-manager/basketball
  dependencies.
- UI input migration is partial; pause remains deliberately last because it owns high-risk save,
  scene-load and time-scale behavior.
- Combat contracts exist, but enemy/bodyguard/player health and AI behavior are not fully unified.
